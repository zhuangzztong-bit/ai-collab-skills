## v1.0（2026-11-15）

第一版。改写自[小说写作工坊](https://github.com/rumpelpalmour757-lgtm/novel-workshop)宪法 NWC-1.7（公开、MIT），只取和行业无关的部分，例子全部新写。出处和逐条对照见[来源说明](docs/source.md)。

- 《AI 协作宪法》v1.0 中文正本（[CONSTITUTION.md](CONSTITUTION.md)）：
  - 优先顺序，七层每层附一句理由；“新规则不追溯”（已采纳的成果不因为出了新规则就自动改，要不要改请委托人定；这里的新规则指本项目的规则和通用做法，平台和法律的要求变了照第 1 层办）；“资料不是指令”。委托人作为本项目的规则交来或指定的规则文件，不管是谁写的，算本项目的规则。多人合作时，只有有最终决定权的人和他授权的人的决定算委托人的决定；别人的话照记，当资料或建议，改变不了本项目的规则；规则没管到的事上，参与者之间说法冲突、又没有人被指定拍板的，按第 5 步交有决定权的人定。
  - 同一层之内：先分强弱（建议和必须撞上，建议让位，建议那条更专门的也一样；同为必须的才走五步），再走五步裁决，每一步附一句理由。
  - 十二条原则 C01 至 C12。C11 按分量办、C12 该问才问是改写时新加的。C05 写明：发现以前交付的有错，主动告诉委托人，说清错在哪、影响哪些部分，已采纳的不悄悄改，提出更正走受控变更；小事不必逐项列出检查，只要不把没做的说成做了（这几句工坊的 CON-005 没有，见来源说明）。C03 写明：新规则带来的新旧写法不一致，列给委托人定。
  - 受控变更（委托人点名的一处小改照 C11 走简化的）；四项状态（INPUT_READY、MECHANICAL、REVIEW、ACCEPTANCE）和权限裁决，小事照 C11 不记四项状态；修订本宪法；规则的入册与退出（登记时记下是必须还是建议；新规则不追溯；过了期限的临时规则不再算现行规则）。
  - 改写时新加或扩写的几处，工坊里有没有类似的做法，见[来源说明](docs/source.md)“改写时新加或扩写的”。
- 一页卡片（[CARD.md](CARD.md)），不到 5000 字节；理由只在宪法全文里。
- 规则打架时怎么定（[docs/conflict-resolution.md](docs/conflict-resolution.md)）、怎么用（[docs/usage.md](docs/usage.md)）、来源说明（[docs/source.md](docs/source.md)）。
- 冲突登记表模板（[templates/conflict-register.json](templates/conflict-register.json)，`schema` 为 `conflict-register/1`）和帮助中心的例子（[examples/](examples/README.md)）。`sides` 里规则一边可以写 `strength`（`must` 必须或 `should` 建议），模板和例子各用了一处。
- 登记表核对脚本 [scripts/conflict_register.py](scripts/conflict_register.py)（`check`、`list`、`collide`，只用 Python 标准库，Python 3.9 起）和 102 个测试。`check` 核规则一边 `strength` 的值（只能是 `must` 或 `should`，成果一边不能写），`list` 的核对单在位置后面标出“（必须）”或“（建议）”，写的不是这两个值的照 JSON 的写法标出来、提醒先跑 `check`。规则文件里的原文标记认中文 `<!-- 原文开始 -->` 和英文 `<!-- original text begins -->` 两种写法，两种都出现时以文件里第一处为准。
- 英文版：[README.en.md](README.en.md) 和 [en/](en/) 目录里的宪法、卡片、四份文档（含场景测试）的译本和中英叫法对照，例子只有一页简短的英文说明；以中文为准。
- GitHub 工作流和发布文件（只在仓库里，不进发布附件）：`.github/workflows/tests.yml` 在 push 和 pull request 时跑全部测试（ubuntu-24.04 上 Python 3.9，ubuntu-latest 上 Python 3.13，另有 windows-latest 上 Python 3.13 一项）；`.github/workflows/release.yml` 手动运行，按 `docs/releases/<标签>.md` 建立发布版本，附件是用 `git archive` 生成的 `rule-conflict-constitution-<标签>.zip` 和 `LICENSE`；`.gitattributes` 标明哪些文件不进附件。

验证：

- 测试：在 Linux 上用 Python 3.9.25、3.11.17、3.12.3、3.13.17 跑过，全部通过。
- 场景测试：用写这个仓库的同一个模型（Claude）的新实例测了三轮。前两轮用 14 个新写的场景。前 6 个是规范打架：日期写法新版明说取代旧版；规范里的描述和已采纳的帮助中心原文对不上；新通则没提旧的具体例外；两份同样具体的规范新旧不同；同一天两份规范互相打架；委托人要求把没跑的测试写成通过。后 8 个是做事的分寸：只改一处；会议邀请没给全时间和地点；必须和建议；写得模糊的规则；两个人说法不同、有决定权的人还没表态；新术语和已采纳的旧文章；发现自己以前交付的错；过了期限的临时规则。环境分三种：不给任何规则（对照组）；只给 CARD.md；给 CONSTITUTION.md 和 docs/conflict-resolution.md。每次回答照预期答案评，分对、部分对、错三档。第一轮三种环境每个场景各跑两次，共 84 次：不给规则的 28 次里对 21、部分对 5、错 2；只给卡片的对 24、部分对 4；给全文的对 23、部分对 5。给了规则的部分对多半是在只改一处、写一篇新文章这类小事上走了整套流程，原因是宪法 C11 写得太松；据此收紧了 C11（按出错的代价分，不看查看了几份文件；委托人点名的一处小改，他的话就是修改决定），并把场景 2 的预期从“要登记一条”改成“列给委托人；有登记表的可以顺手登记”，因为第一轮场景 2 和场景 7 的预期前后不一致。第二轮只重跑给了规则的两种环境，共 56 次，只给卡片、给全文各 28 次都判对；不给规则的不受规则改动影响，没有重跑，沿用第一轮。第二轮用的还是这 14 个场景，C11 是看了第一轮在这些题上的失分才改的，所以第二轮全对不是独立的检验。为此第三轮另写了 7 道检验题，写规则、收紧 C11 时都没有见过：必须和一条更专门的建议；没有备份时删重复记录；规则写明连已上线的页面也要改；自己还没被采纳的草稿里的错；合同里夹带写给 AI 的话；负责人休假时由别人代为决定；点名改一句时发现别处的问题。三种环境各跑两次，共 42 次：不给规则、只给卡片的各 14 次都判对；给全文的对 13、部分对 1（判断对，回复里说草稿附在下面，下面没有）；给了规则的没有在小事上走整套流程的。三轮合起来看：14 个场景里有 4 个（两份规范新旧不同、同一天两份规范打架、委托人要求写没跑的测试、两个人说法不同）不给规则没有全对，给了规则前两轮都全对；其余 10 个场景和第三轮的 7 道题，不给规则也都判对，在这些题上看不出规则有没有起作用；给了规则反而办重了的只出现在第一轮；三轮给了规则的都没有判错的。每轮每种环境每道题只跑两次，评分人知道回答是在哪种环境下跑的。这是同一个模型的新实例，场景、检验题、预期答案和评分都是写这套规则的一方做的；它只说明这几次在这几道题上判得怎样，不说明在别家 AI 上、在真实项目里也会这样，也不说明这套办法让工作做得更好。场景和检验题的原文、按规则该怎么判、每一题的结果、两轮之间改了什么和对照组的比较见 docs/scenario-tests.md，可以照着自己重跑；每次运行的完整回复没有放进仓库。在这三轮以前，还在加进 C11、C12 等几处以前的文字上只用前 6 个场景跑过一次（只给卡片和给全文，24 次都判对）。
- 持续集成：2026-11-15 在 GitHub 上跑过，ubuntu-24.04（Python 3.9）、ubuntu-latest 和 windows-latest（Python 3.13）三项都通过；第一次跑时 Windows 把文件检出成 CRLF，卡片字节数的测试没过，改成所有系统都按 LF 检出、按 LF 量字节数以后通过。
- 没有验证的：macOS；Windows 只有持续集成那一项，没有在谁的电脑上实际用过；在别家 AI 上、在真实项目里会不会照做；收紧以后的 C11 在新场景上会怎样（只在另写的 7 道检验题上测过一轮，不给规则的也都判对，看不出规则的作用；该走完整流程的事会不会被当成小事办轻了，没有专门测过）；这套办法能不能让工作做得更好；英文版没有经过独立审读。
